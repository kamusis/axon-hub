# Mopheus Customer Technical QA & Requirement Triage

Use this workflow whenever answering customer questions, presales technical inquiries, RFP capability tables, or requirement evaluations for Mopheus.

## 1. Mandatory 3-Layer Fact Verification (Never Guess from Memory)

Before writing a single answer, verify facts in strict precedence order:

1. **Executable Source Code & Migrations (Highest Authority)**:
   - **Database & Extensions**: Check `server/migrations/*.sql` (including the latest migrations) and `server/internal/repo/*.go`. Never assume an extension or column exists without checking if a later migration dropped it.
   - **Core Packages & Services**: Check `server/pkg/`, `server/internal/service/`, `server/internal/http/`, and `server/models/`.
   - **Test Suites**: When asked about benchmarks, stress tests, or E2E coverage, inspect `tests/performance/` and `tests/e2e/` directly. State explicitly what scenarios are covered vs. not yet covered.
   - **Latest Remote Main**: Run `git fetch origin main` and check recent commits on `origin/main` so newly merged capabilities (e.g., auth/security features) are not misreported as unsupported.
2. **Product Documentation (`packages/docs-content/zh-Hans/`)**:
   - Check user-facing product docs in `packages/docs-content/zh-Hans/` before internal `docs/*.md`.
   - Internal `docs/*.md` files may contain early RFCs or superseded proposals. Whenever an internal `docs/*.md` file contradicts current code, **immediately add an inline `> [!IMPORTANT]` or `> [!NOTE]` annotation** to that doc recording the current implementation while preserving historical context.
3. **Mopheus `dev-space` Design Tickets (`mop` CLI)**:
   - For any capability not yet in production code, search `dev-space` tickets before answering:
     ```bash
     mop ticket list -w dev-space --search "<keyword>"
     mop ticket get <ticket-uuid> -w dev-space
     ```
   - Distinguish three states clearly:
     - **Already implemented in production**: Cite the real mechanism (`server/pkg/okf/`, `zhparser`, etc.).
     - **Architectural design completed in `dev-space`, awaiting scheduling**: Present the concrete designed mechanism (e.g., `.moppkg` / `.mopbackup`, Ed25519 signing, AES-256-GCM encryption) and state that the architecture is finalized and scheduling is prioritized by demand.
     - **Not planned / out of scope**: State boundaries clearly or propose integration via Webhook / REST API / CLI / Skill.

## 2. Technical Skepticism & Pushback on Pseudo-Requirements

Do **not** blindly pander to every customer request or force-fit unrelated features to make a bad idea sound feasible:

1. **Diagnose the Underlying Problem**: Ask whether the customer's proposed interaction model is realistic in production AI engineering.
2. **Push Back Professionally on Anti-Patterns**:
   - Example: If a customer asks to replace prompt writing in complex IT operations with "step-by-step A/B/C/D multiple-choice questions generated by the agent", do **not** promise a multiple-choice wizard loop.
   - Explain clearly why complex operations cannot be reduced to static multiple-choice trees (and why a user who cannot express intent cannot safely judge low-level A/B/C/D operational branches either).
   - Redirect to Mopheus's real product paradigm: **Domain Asset Packages (`Agent` + `Skill` + `Scheduled Job`)** encapsulate domain SOPs, scripts, and diagnostic decision trees inside Skills and Agent instructions, so end users only provide the target object or trigger a scheduled/one-click task.

## 3. Customer-Facing Communication Hygiene

1. **Never Expose Deprecated Internal Transitions**:
   - If an internal technology was removed or replaced (e.g., `pgvector` replaced by PostgreSQL full-text search `zhparser` + `pg_bigm` + `pg_trgm`), state **only what Mopheus currently uses and why it fits the architecture**.
   - Never tell customers "we used to have X but removed it in migration Y". To external customers, deprecated internal experiments never existed.
2. **Strict 1-to-1 Question & Answer Structure**:
   - When extracting questions from customer documents or screenshots, use a clean flat list:
     - `### 问题 N：<Original Customer Question>`
     - `[上下文]：<1-line document context>`
     - `**回复**：<Direct, concise, technically rigorous answer>`
   - Do not invent extra wrapper chapters, marketing fluff, or unrequested summary tables.
